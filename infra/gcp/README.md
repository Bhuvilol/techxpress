# Google Cloud setup

`setup.sh` creates everything the VORTEX API needs in one project, in `asia-south1` (Mumbai). It is safe to re-run: it creates what's missing, re-applies configuration, and never deletes anything, replaces the deployed image or changes an existing secret.

**Review the script before running it.** It creates billable resources, mainly Cloud SQL (about $55–65 a month) and one always-on Cloud Run instance.

## What it creates

| Resource | Name | Notes |
|---|---|---|
| Cloud SQL, PostgreSQL 16 | `vortex-db`, database `vortex`, user `vortex_app` | 1 vCPU / 3.75 GB, 10 GB SSD (auto-grows), daily backups 21:30 UTC kept 7 days, point-in-time recovery 7 days, Sunday maintenance, deletion protection. Public IP with **no** allowed networks: only the Cloud SQL connector can reach it. |
| Artifact Registry | `techxpress` | Docker images; keeps the newest 20 |
| Secret Manager | `DATABASE_URL`, `ACCESS_TOKEN_SECRET`, `CF_EMAIL_API_TOKEN`, `ADMIN_SEED_PASSWORD`, `STAFF_SEED_JSON` | The first two are generated by the script; you add the other three |
| Service account | `vortex-api@` | Runtime: Cloud SQL client, log/metric writer, reads only those secrets |
| Service account | `github-deployer@` | CI: deploy Cloud Run, push to `techxpress` only, act as `vortex-api@` only |
| Workload Identity Federation | pool `github`, provider `github-oidc` | Accepts GitHub tokens only from the repository's numeric ID **and** `refs/heads/main` |
| Cloud Run service | `vortex-api` | 1 instance (min = max = 1), session affinity, 3600 s timeout, 1 vCPU / 1 GiB, concurrency 1000, public. Starts with a placeholder image until CI deploys. |
| Cloud Run job | `vortex-migrate` | `npx prisma migrate deploy`; CI runs it before every deploy |
| Cloud Run job | `vortex-seed` | `node prisma/seed.js`; run by hand. Created once its secrets exist. |
| Monitoring (stage `monitoring`) | uptime check `vortex-api-health` + 5 alert policies | Health check every minute; Cloud SQL CPU/disk > 80 %; API 5xx > 2 %; concurrency > 800 |
| Budget (stage `budget`) | `techxpress monthly` | Emails billing admins at 50 / 90 / 100 % |

The one-time `vortex-reset` job is **not** created here; [docs/RUNBOOK.md](../../docs/RUNBOOK.md) creates it on the day it's needed.

## Steps

### 1. Prerequisites
- Install the Google Cloud CLI: `brew install --cask google-cloud-sdk`
- Sign in with an account that is **Owner** on the project (or Editor + Security Admin + Service Account Admin): `gcloud auth login`
- Billing linked to the project.
- `gh` signed in (used to look up the GitHub repository ID), or set `GITHUB_REPO_ID` yourself.
- The new GitHub repository exists.

### 2. Configure
```sh
cp infra/gcp/config.env.example infra/gcp/config.env   # git-ignored
# fill in PROJECT_ID, GITHUB_REPO, ALERT_EMAIL, ADMIN_SEED_EMAIL, ...
```

### 3. Core resources
```sh
./infra/gcp/setup.sh core
```
At the end it prints the four GitHub repository variables. Add them under **Settings → Secrets and variables → Actions → Variables**: `GCP_PROJECT_ID`, `GCP_REGION`, `WIF_PROVIDER`, `DEPLOYER_SA`.

### 4. Add the remaining secrets
Type values at a hidden prompt so they never land in shell history:
```sh
add_secret() { read -rs -p "$1: " v && echo && printf '%s' "$v" | gcloud secrets versions add "$1" --data-file=- && unset v; }

add_secret ADMIN_SEED_PASSWORD     # 12+ characters, unique
add_secret CF_EMAIL_API_TOKEN      # Cloudflare token with only "Email Sending Write"

# The staff list is JSON; load it from a local file, then delete the file:
gcloud secrets versions add STAFF_SEED_JSON --data-file=staff.json
```
`staff.json` format (coordinators need an institution that exists in `services/api/prisma/data/taxonomy.json`):
```json
[
  { "fullName": "Asha Rao",   "email": "asha@example.org", "role": "JURY" },
  { "fullName": "Ravi Kumar", "email": "ravi@example.org", "role": "COORDINATOR", "institution": "ITER | SOA" },
  { "fullName": "Second Admin", "email": "ops@example.org", "role": "ADMIN" }
]
```
Then re-run `./infra/gcp/setup.sh core`: it attaches the Cloudflare token to the service and creates the `vortex-seed` job.

### 5. First deploy
Push to `main`, or run **Actions → Deploy API → Run workflow**. It builds the image, runs `vortex-migrate`, deploys `vortex-api` and checks `/api/health`.

### 6. Seed
```sh
gcloud run jobs execute vortex-seed --region asia-south1 --wait
```
Staff login codes then appear on **Admin → Staff** in the portal.

### 7. Monitoring and budget
```sh
./infra/gcp/setup.sh monitoring   # after step 5, when /api/health returns ok
./infra/gcp/setup.sh budget       # needs BILLING_ACCOUNT_ID and BUDGET_AMOUNT
```
Google sends a confirmation email to `ALERT_EMAIL`'s inbox the first time; no action is usually needed.

### Changing configuration later
Edit `config.env` (for example `CORS_ORIGIN`, `APP_URL`, `MAIL_FROM` once the domain is live) and re-run `./infra/gcp/setup.sh core`. That creates a new revision with the same image.

### Event days: more CPU
```sh
gcloud run services update vortex-api --region asia-south1 --cpu 2 --memory 2Gi
# afterwards
gcloud run services update vortex-api --region asia-south1 --cpu 1 --memory 1Gi
```
